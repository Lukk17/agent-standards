# Partial Upgrades and Mirror 404s

Read this when a download fails with 404 or "failed retrieving file", when dependencies cannot be satisfied right after a sync, when a program fails with a missing `.so`, or when AUR builds start failing after an upgrade. The rules live in [SKILL.md](../SKILL.md).

---

### The usual story

A full upgrade started while the mirror was still syncing, so some packages of a set such as KDE Frameworks were new on the mirror and others were not there yet. Downloads returned 404 and AUR builds failed against a mixed set of libraries. The fix is to run the full upgrade again once the mirror is complete. Nothing gets reinstalled by hand.

---

### Triage, in order

1. Take the exact URL from the error text and request that URL, not a neighbouring one: `curl -sI '<url from the error>'`. A 404 on that file means the mirror does not have it yet or no longer has it. A 200 means the problem is not the mirror. Never conclude from a different path on the same host.
2. Find which mirror pacman used. Each repository section in `/etc/pacman.conf` names an `Include` file. The first `Server` line in that file is tried first, and pacman falls through the rest on failure. `pacman-conf --repo-list` lists the repositories.
3. Do not rely on a mirror's `lastsync` file, which some mirrors do not maintain. Compare versions instead: `pacman -Si <pkg>` shows the version in the synced database, and `ls -l --time-style=long-iso /var/lib/pacman/sync/` shows when each database was fetched.
4. Wait and retry. A mirror that is mid-sync normally finishes within hours. Then the owner runs `sudo pacman -Syu`.
5. If the same URL still 404s hours later, or one mirror is simply slow, rank the mirrors again. Check whether the mirrorlist is generated by reading its header. A generated list is regenerated with the tool that wrote it (`reflector`, `rate-mirrors`, or a derivative's wrapper), never hand-edited. Read the tool's `--help` before running it, then `sudo pacman -Syyu`. The doubled `y` forces a database refresh and is the only legitimate use of `-yy`, and only together with `u`.
6. Never fix a 404 with `pacman -Sy <pkg>`, `--overwrite`, `-Rdd` or `IgnorePkg`. Each turns a transient error into a permanent partial upgrade.

---

### Recognising a partial upgrade that already happened

Typical signs: `error while loading shared libraries: libfoo.so.N: cannot open shared object file`, a package that needs a newer dependency than the repository offers, Qt, KF6 or Plasma components on mismatched versions, AUR builds that worked last week and now fail at link time.

1. Find the unequal versions. For KDE: `pacman -Q | grep -E '^(kf6|plasma|kwin|qt6-base|libplasma)' | head -40`. Frameworks share one version family, Plasma components another, and Qt 6 one release.
2. Find broken links in one program: `ldd "$(command -v <program>)" | grep 'not found'`.
3. Find packages with missing files: `pacman -Qk 2>&1 | grep -v ' 0 missing files'`.
4. Repair by completing the upgrade, never by pinning: `sudo pacman -Syu`. If a library really was removed or renamed, reinstall the packages that link to it after the upgrade, or rebuild them for the AUR with `paru -S <pkg>`.
5. After the upgrade finishes, run `pacman -Qtdq` and `systemctl --failed`, see [systemd-journal-triage.md](systemd-journal-triage.md).

---

### If the upgrade itself was interrupted

Power loss, a closed terminal, or a killed process in the middle of a transaction.

1. If the machine is still up, do not reboot yet. Check `pgrep -a pacman`.
2. If the lock file is stale and no pacman process runs, the owner removes it, see [pacman-discipline.md](pacman-discipline.md).
3. The owner runs `sudo pacman -Syu` again, which completes the upgrade. If errors name a corrupted package file in the cache, remove only that file from `/var/cache/pacman/pkg`. `pacman -Scc` is far too broad.
4. For kernel or initramfs trouble the owner regenerates with `sudo mkinitcpio -P`, followed by whatever the bootloader needs. On CachyOS with Limine, the `cachyos` skill covers that step.
5. If the machine no longer boots, roll back with [snapper-rollback.md](snapper-rollback.md) or use a live ISO and a chroot.

---

### Leftover download directories

Failed or interrupted downloads can leave `download-XXXXXX` directories in `/var/cache/pacman/pkg/` that the owner's account cannot enter, which also makes `du` print permission errors. They are safe to remove when no pacman process is running, with the owner's approval. UNVERIFIED as a general pacman behaviour, observed on one host:

```bash
sudo find /var/cache/pacman/pkg -maxdepth 1 -type d -name 'download-*' -exec rm -r -- {} +
```
