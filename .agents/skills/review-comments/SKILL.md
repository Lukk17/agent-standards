# Review Comments

How to word what we write on a pull request: the review comments we leave on other people's pull requests, the replies we write to review comments on our own, how every draft is shown and posted, and how other people's comments are laid out in chat while we work through them. This skill only decides how a finding is said.

### When not to activate

- Finding what is wrong in the diff, use `code-reviewer`
- Writing or editing a pull request description, use `git-workflow`
- Merging, triaging, investigating CI or cutting a release, use `github-ops`

---

### Before writing

Comment only on what the pull request changes. Read every linked pull request first, and skip anything a later one fixes.

---

### Rules for comments and replies

1. Keep every comment and every reply to one to three sentences.
2. Write in a polite, friendly, human way. Say what is wrong, if anything, and nothing else, with no filler such as "thanks", "good catch" or "fair point".
3. For a point that must be fixed, stay friendly but firm, and say clearly what has to change.
4. Put a point that is not about one line in a normal conversation comment. Give each small point its own comment on its own line.
5. An approval carries no praise, and it does state the build result.
6. A reply says only that the point is fixed, how in a few words where needed, or why it is not fixed.
7. Back a reply with a decision record, a project document or a ticket. When the work moved to later, name the ticket.
8. Never refer to a decision number from a chat, because nobody reading the pull request saw that chat.
9. Explain every abbreviation at its first use in each comment and each reply, such as PoC (proof of concept), even when an earlier message already explained it.

---

### Drafts and posting

Rules 1 to 6 below are kept word for word the same in `git-workflow`, so change both copies together.

1. Print every draft of a review comment, a reply or a pull request description in full in the chat, numbered, and never store a draft in a file.
2. Post nothing until the user has approved it.
3. Leave no trace of an AI agent or tool in a review comment, a reply or a pull request description: no "by Claude", no "generated by", no co-author line.
4. Never name a commit hash in a review comment, a reply or a pull request description.
5. Use real issue and pull request numbers, never a placeholder.
6. Use no em dash, no en dash, no semicolon joining two clauses, no bold and no italic.
7. Post replies only after every fix is done, green and pushed.

---

### Chat layout for other people's comments

When working through the comments other people left on our code, show each one in the chat in this order:

1. A horizontal line.
2. The file name and the line number, as `path:line`.
3. The comment, quoted.
4. Our response to that comment.

Put a blank line before the horizontal line and between each of the four, because the chat renders markdown: a `---` right under a line turns that line into a heading, and a line right after the quote joins the quote.
